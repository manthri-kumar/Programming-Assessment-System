# Isolated worker integration

`backend.container_runner.ContainerRunner` is the API-side control-plane adapter. It accepts only Python, C, or Java jobs, generates a unique opaque job ID, requires a reviewed `sha256` image digest, and always requests cleanup in a `finally` block. It has no host compiler or process fallback.

`backend.worker_http.MtlsWorkerEngine` implements the selected local control channel. It accepts only an HTTPS origin whose hostname matches the configured certificate identity, loads a project CA and client certificate, requires `worker-policy-v1`, bounds every response, and validates the exact image/toolchain readiness response. `ASSESSMENT_WORKER_CONFIG` enables this path; missing or malformed configuration retains `FailClosedRunner`.

The adapter serializes only allowlisted job fields into a bounded canonical JSON request. It rejects non-finite values, oversized messages, mismatched job IDs, unknown or duplicated outcome IDs, unexpected weights/statuses, invalid exit codes, and oversized response streams. Engine execution and cleanup failures are converted to explicit runner-unavailable errors. This protects the backend boundary but does not itself prove worker isolation.

The `IsolatedEngine` implementation remains an external security boundary. It must transfer source through its protected channel, stream and cap output, enforce aggregate and per-stage deadlines, terminate the entire container/process tree, and prove workspace removal. The API process must not receive a Docker socket or let request fields control engine commands.

`ContainerPolicy.isolation_arguments` records the required flags: no network, read-only root, all capabilities dropped, no-new-privileges, numeric unprivileged user, PID/memory/CPU limits, an init process, and a bounded `nosuid,nodev` tmpfs. The tmpfs must permit execution because C binaries are compiled inside it. There are no host bind-mount arguments. `worker/policy.example.json` intentionally contains no usable digest; deployment remains fail-closed until a reviewed image digest and engine are configured.

`worker/control_service.py` runs only as a dedicated non-root Linux account and owns rootless Podman. It retains expected outputs and weights outside the container, removes those fields from the container payload, verifies an immutable local-registry image plus exact toolchain labels and a hash-pinned seccomp profile, and constructs all isolation arguments itself. `worker/entrypoint.py` is the container-only one-job protocol. It validates the reduced input again, uses fixed Python 3.11/Clang 14/JDK 17 commands, caps compiler and program streams while reading them, applies per-stage and aggregate deadlines, starts each subprocess in a new process group, kills that group on timeout/output overflow, and removes the unique workspace in `finally`. The container cgroup remains responsible for memory, PID, CPU, and scratch enforcement. Unit tests inspect this protocol without invoking submitted source; only real-worker tests can prove the combined behavior.

Unit tests verify policy construction, strict request/response validation, unique job IDs, simulated language/outcome handling, cleanup calls, concurrent workspace naming, and fail-closed behavior. They inject a process executor and therefore never execute submitted source on the host. Those tests do not establish real containment. Tasks requiring network, filesystem, memory, process, timeout, stale-artifact, and cleanup evidence remain blocked until the worker is independently exercised.
